## Pre-commit Hook: Conventional Commits

To ensure all commits in the project follow the [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/) standard, install the hook:

```bash
# Copy hook into the project and set up in git
mkdir -p .husky .git/hooks
cp .github/.husky/commit-msg .husky/commit-msg .git/hooks/commit-msg
chmod +x .git/hooks/commit-msg

# Verify
echo "feat: test" > /tmp/test.txt
.git/hooks/commit-msg /tmp/test.txt
```

> `commit-msg` runs after the commit message is written — this is the correct hook for validation. `pre-commit` doesn't work because it runs before the message is written.

**Supported types**: `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`, `revert`

**Formats**: `type: message`, `type!: message`, `type(scope): message`, `type(scope)!: message`

**Length limit**: 88 characters in subject line (warning at >72).

**Exceptions**: commits matching `release vX.Y.Z` skip validation (automatically generated by release scripts).

## Release

The shared `reusable-release.yml` workflow owns version resolution, changelog generation/promotion, checksums, and GitHub Release publication. Consumer repositories keep project-specific build, artifact collection, and Docker jobs in their own thin `release.yml` wrapper, then pass an optional uploaded artifact to the reusable workflow.

Releases are automatically cut from `CHANGELOG.md` following [Keep a Changelog] + [SemVer] rules.

1. Add changes to `## [Unreleased]` under the appropriate categories: `Breaking`, `Added`, `Changed`, `Fixed`, etc.
2. Preview what will happen: `make release-dry-run`
3. Cut the release: `make release`
4. Push: `make release PUSH=1`

Categories determine the version type:
- `Breaking`, `Removed` → major
- `Added`, `Deprecated` → minor
- `Fixed`, `Changed`, `Security` → patch

[Keep a Changelog]: https://keepachangelog.com/en/1.1.0/
[SemVer]: https://semver.org/spec/v2.0.0.html
